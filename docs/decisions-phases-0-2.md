These are decisions made without the author present, during autonomous
execution of the implementation plan on 2026-08-30 and 2026-08-31. Each
records what was decided, why, and what it costs if the decision was wrong.
They are preserved here rather than in a session log because several of them
bind later phases and several belong in the manuscript.

Rulings that a later phase must honour are marked CARRIES FORWARD.

## R25. the purpose/field cross-product overgrant is a REAL SEMANTIC DEFECT in my design and must be fixed in a Task 9 fix round, not routed forward as the reviewer suggested. The finding: compilePolicy emits benefits:purpose and benefits:fieldSet as two independent ANDed isPartOf constraints, but conformance/README.md defines consent as a triple relation where a grant covers a field only when field, purpose and recipientClass all match. Given grants where field A is consented for purpose X and field B for purpose Y under one recipient class, the existing single-recipient-class guard does not reject the input and the emitted policy authorises (B, X) and (A, Y), which were never consented. Why this is load-bearing rather than deferrable: the project's central claim is that one consent model is enforced identically at two points. S1 enforces the triple. S2 as compiled enforces the cross-product. If they disagree the claim is false, and this is exactly the kind of defect a journal reviewer probes. THE FIX: add a single-purpose guard mirroring the existing single-recipient-class guard, throwing when grants span more than one purpose, and emit benefits:purpose with operator eq on a scalar rather than isPartOf on a list. This is correct rather than merely restrictive, because a release request carries exactly one purpose: the mock IAM supplies a single benefits.requester.purpose claim, and Task 12's PurposeFunction evaluates one claim value. A caller holding multi-purpose grants must compile one policy per purpose, which is the accurate model. Task 12's PurposeFunction already handles EQ as well as IN, so the interface change is compatible. Cost if wrong: if a legitimate release ever needs to span purposes, the guard must be replaced by one permission per (purpose, recipientClass) pair, which is a larger change to make later than now.

## R29. fix the missing defensive copy now. The finding: StewardAuthorization is a record whose List<StewardSignature> component is stored by reference with no compact constructor, so a caller retaining a mutable list can change distinctStewardCount() on an already-saved authorization without going through the store at all, bypassing it as the source of truth for a security-relevant record. ## R30. do NOT build atomic append for the lost-update race; document the precondition instead. The finding is real: save() does an unconditional Map.put, so two stewards co-signing near-concurrently through a read-modify-write cycle would silently lose a signature. Why not fix now: within phases 0 through 5 there is exactly one writer, the single-threaded startup seeder that Task 14 adds, writing once per release request, so the race is unreachable in the system as built. The accumulating write path is a steward portal that belongs to Phase 6. Building concurrency machinery for a component that does not exist is speculative work, and it is the same shape as the limitation the spec already states for the audit chain's single writer. What I am requiring instead: an explicit contract on StewardAuthorizationStore.save stating that it REPLACES any existing authorization wholesale, that the caller must be the sole writer for a given releaseRequestId, and that accumulating signatures over time requires an atomic append operation which Phase 6 must add. A documented precondition makes the current code correct by contract; an undocumented one is a trap. Cost if wrong: if Phase 6 adds a portal without reading the contract, signatures can be silently lost; the mitigation is that this ruling and the interface javadoc both say so, and it is recorded as a Phase 6 requirement and a manuscript limitation.

## R38. pre-authorise a specific remedy for the most likely Task 14 failure, so the implementer does not have to guess under pressure.
