## P8. fix the group-key separator collision NOW, in a fix round, rather than deferring. The finding is mine, inherited verbatim from my plan. KAnonymity builds its group key by joining attribute values with "|", so a value containing "|" collides two semantically distinct groups into one key. The reviewer's example is concrete: with groupBy [channel, service], a row with channel "x|y" and service "z" produces the same key as a row with channel "x" and service "y|z". This is a PRIVACY failure, not a correctness nicety: if each component group holds fewer than k participants and would correctly be suppressed, the merged group can clear k and be released, and an adversary who can bound one component recovers the other by subtraction. That is a differencing attack against the exact suppression guarantee this module exists to provide. Why now: the group-key format is consumed by four later tasks, so the cost of changing it rises with every one of them, and Task 6 already emits it into the stored artifact's JSON. Why escaping rather than a structured key: escaping is roughly five lines and keeps GroupedCount a String, so nothing downstream changes, whereas a List-valued key would ripple through the artifact format and the end-to-end probe. Cost if wrong: escaped values appear in the emitted JSON when a value genuinely contains the separator, which is honest output rather than a defect, and the reference implementation's own data (channel values like app, sms, paper, voice) will never trigger it. 

## P9. batch the reviewer's Minor into the same round. The distinct-participant fixture repeats one participant with byte-identical rows, so it also passes a whole-row-deduplication implementation and its discriminating power is narrower than its name claims. ## P10. fix the negative-infinity edge case. The finding: java.util.Random.nextDouble() can legitimately return exactly 0.0, with probability 2 to the power -53, giving u = -0.5, then 1 - 2|u| = 0, then Math.log(0) = negative infinity, so noise() returns -Infinity. The reviewer verified this by instrumenting a Random subclass rather than by inspection. This is MY code, reproduced verbatim from the plan. It is distinct from the floating-point side channel the spec scopes out: that term means Mironov-style precision leakage, a subtle statistical attack, whereas this is an unbounded non-finite output that would poison every downstream composition, since count + (-Infinity) is -Infinity and the stored artifact would carry it into the released JSON. Fix by rejecting and resampling the single excluded point, which is the standard treatment and costs three lines. Cost if wrong: none; resampling a measure-zero point changes the distribution not at all and the guard is exercised by a test. 

## P11. document the determinism contract, batching the reviewer's Minor into the same round. Its point is sharper than it first appears. java.util.Random is thread-safe, so concurrent use cannot corrupt state, but if a later pipeline shared one LaplaceNoiseSource across concurrently processed groups, the ORDER in which threads consume draws becomes scheduling dependent, and byte-identical reproducibility silently disappears. That reproducibility is exactly what Task 12's final gate asserts, so an undocumented contract here would surface as an unexplained gate failure much later. Task 6's pipeline iterates groups sequentially so nothing is wrong today; a Javadoc line prevents a future change from destroying the property invisibly. Cost if wrong: none, it is documentation. 

## P12. strengthen the concurrency test before review, because the implementer's own finding shows it is a weak regression detector. The test passes reliably against correct code but catches the naive read-then-write implementation only about 15 percent of the time per run, since 50 threads on a 16-thread pool do not all overlap. That matters more here than it would anywhere else in this project: this accountant is the one component where a silent regression is a privacy violation rather than a data problem, so a detector that fires on roughly one run in seven is weak protection for exactly the property we declared non-negotiable. Two cheap changes fix it: size the pool to the thread count so every thread genuinely contends, and repeat the whole race within the test, asserting the invariant on each iteration. Detection probability then approaches certainty. Cost if wrong: the test takes a second or two longer, which is nothing against a suite that already starts JVM connectors elsewhere. Addressing this BEFORE review rather than after, per the skill's handling of a correctness concern raised in a DONE report. 

## P13. fix the missing JSON escaping. This is the highest-value finding of the phase so far and it is a direct consequence of P8. Task 3's separator escaping puts backslashes into group keys, and PrivacyPipeline writes those keys into JSON by raw string concatenation, producing three distinct failures. A value containing "|" becomes "\|", which is not a legal JSON escape sequence under RFC 8259, so a strict parser rejects the whole document. A value containing a double quote breaks out of the string literal entirely, permitting structure injection from an attribute value. And a value containing a backslash is doubled to "\\", which IS valid JSON and parses back to a single backslash, silently undoing KAnonymity's injectivity so a consumer splitting the parsed group name on "|" reconstructs the wrong identity with no error. The reviewer notes this would be Critical had I not mandated it. Fixing a privacy defect in Task 3 created a serialisation defect in Task 6, which is precisely the class of interaction only visible across task boundaries. Cost if wrong: none, escaping is standard and adds no dependency.
